# 决策记录

## 2026-08-17 外勤岗位类别与荣誉身份轨道分层建模

- `role_type` 继续表示荣誉身份轨道，值域为 `个人`、`主管`、`经理`；它不能用于判断人员本身是管理职还是专员。
- 新增 `staff_category` 作为人员岗位类别，值域为 `专员`、`外勤管理职`，由人力表职等/职级识别并写入荣誉源人力、人员月度和人员汇总底表。
- 管理职人员可同时具有个人轨道和主管/经理团队轨道；两条轨道的 `staff_category` 均为 `外勤管理职`。专员与管理职展示、历史明细和机构结构优先使用 `staff_category`，避免将管理职个人轨道误归为专员。
- 存量批次通过同批次、同年月、同人员、同业务线的人力源记录回填岗位类别；无法关联时才按身份轨道兜底，不删除、不重算历史星钻结果。

## 2026-08-03 星钻月末快照与最终结果按回销观察期分开

- 星钻数据版本按 `source_cutoff` 派生为四类：早于月末为“过程数据”，等于月末为“月末快照”，晚于月末为“回销观察更新”，留空为“最终结果”；不新增数据库字段，不改变历史批次。
- 月份选择继续只读取已有成功批次，不因查看月份自动计算或写库。月份已经结束且缺少月末快照时，仅向有重算权限的用户提供“生成月末快照”，重算截至日固定为该月最后一天。
- 月末快照覆盖整月业绩，但不代表45天回销观察已完成。最终结果最早生成日统一为当月最后一天加45天，并且必须使用届时已更新的回销数据重新计算。
- 在最终结果最早生成日前，留空截至日的重算请求由后端阻断，避免把过程值或月末快照误标为最终结果；当前月份尚未结束时也不得提前生成未来月末快照。
- 历史上已存在的无截至日批次不删除、不自动改写。若其创建时间早于观察期结束，页面明确提示需核对当时回销数据，不把该批次包装为已完成观察的结果。

## 2026-08-14 模型路由继续采用Flash与Pro互补，不因单点网传全切Flash

- “效能”拆分为能力质量、工具链兼容、墙钟耗时、调用成本和返工率，不能用单个代码任务、主观体感或单期报告替代本项目长期数据。
- DeepSeek官方当前同模式评测不支持Pro能力全面落后：Pro在中文事实问答、复杂推理、长上下文、网页深搜和多数工具任务上总体领先；社区报告的空响应、工具调用落入正文等问题按兼容风险管理，不能直接外推为所有任务质量倒挂。
- 项目内两份9分以上报告呈互补结果：`market-20260814-121537`需要Pro升级修复后达到9.6分；`market-20260814-171105`由Pro主研后经Flash首修发布。若全切任一模型，都会移除已经真实生效的质量兜底。
- 维持Flash来源侦察、Pro主研、Flash首修、Pro升级兜底；9.0发布门槛、独立来源核验和旧报告保护不变。连续六期首次成功率低于80%、Pro兼容失败或Pro质量收益无法覆盖时延成本时，再评估Flash主研或临时Flash-only；恢复或变更必须有项目内对照数据。

## 2026-08-14 市场研究以持久化运行台账和确定性管理摘要进入连续观察

- 单期9分只证明报告可发布，不能代表研究系统已经稳定。每次成功或失败尝试都写入独立运行台账；成功报告同时固化耗时、首次成稿、修复次数、Pro升级、模型调用、CLI估算成本和来源侦察摘要，支持连续六期比较。
- 来源价值按执行摘要、变化信号、研究模块和行动的真实`evidenceIds`引用关系计算，形成引用覆盖率、一手来源占比、公众号/知乎实际使用数和高贡献来源；接入数量不等同于研究贡献。
- 页面首屏的三个核心判断、两个重点监测和三项优先行动由已发布报告确定性提炼，不新增模型调用、不修改报告事实，也不替代详细证据和历史轨迹。
- 行动到期后不得静默顺延复核日期；下一期研究须记录验收结果、未达节点或证据缺口。页面按当前日期提示到期行动，但实际完成仍必须由内部证据支持。
- 连续观察目标保持六个成功周期；首次成稿成功率目标不低于80%。失败尝试纳入运行成功率和首次成功率分母，防止只统计最终成功报告而高估可靠性。

## 2026-08-14 代码发布采用迁移驱动的低停机刷新策略

- SQLite Online Backup API支持读取运行中的WAL库，数据库一致性备份、SHA256和完整性校验前置到主服务停机之前；只有代码切换、必要迁移、目标保护和启动健康检查进入维护窗口。
- requirements文件未变化、现有生产venv可执行且`pip check`通过时复用该环境；依赖发生变化或环境异常时，在服务在线期间建立候选venv，停机后原子切换，并保留旧venv到新服务健康检查通过。
- 现有生产库不再每次发布机械重建全部聚合。部署前后比较`schema_migrations`中`requires_aggregate_rebuild=1`的版本，只有本次新增强制迁移或显式设置`REBUILD_AGGREGATES=1`时重建。
- 新增聚合表、聚合字段或改变历史聚合结果的逻辑，必须新增唯一迁移版本并标记`requires_aggregate_rebuild=1`；该标记优先于`REBUILD_AGGREGATES=0`，防止人为快速发布绕过必要重算。
- 主服务恢复并通过真实`/api/health`后，再同步独立市场研判单元；Nginx配置通过后使用reload而非restart，避免附属步骤和代理切换延长主看板停机时间。

## 2026-08-14 知乎仅通过官方API发现并按C级观点证据接入

- 知乎内容发现只调用数据开放平台公开的`zhihu_search`接口，不抓取知乎搜索页、不调用非公开接口，也不使用登录Cookie或验证码绕过。
- API返回项只是候选线索，必须再次访问公开文章直达页并通过既有标题、正文证据锚点、发布时间和内容哈希门禁后才能交给Pro。
- 首期不依据平台认证标识自动提升证据等级。知乎机构号、专家和普通作者内容统一按C级观点证据处理，不能替代宏观/监管A级原文或同业公司/协会B级一手证据。
- 知乎API限流、鉴权失败、返回结构变化或候选原文不可访问时只记录降级摘要，原Flash侦察和Pro主研继续运行；密钥仅存于服务器受保护环境文件。

## 2026-08-14 公众号作为严格B级证据并采用Flash前置侦察

- 公众号内容纳入寿险市场研判，但不设置数量硬指标。只有公开直达文章且标题、账号主体、正文锚点和内容哈希独立核验通过时，才作为B级一手证据发布。
- 搜索摘要、转载、账号主页、登录/验证码/环境异常页只作为发现线索；原文不可复核时优先使用同主体官网镜像并按实际类型归档，否则披露缺口。
- Flash负责高覆盖来源侦察，程序在Pro主研前并发核验候选；Pro负责跨层、跨期和条线综合判断。该分层降低坏链接返工和Pro搜索成本，但不降低最终全量来源验证及9分发布门槛。
- 前置侦察属于可降级优化层。Flash或候选核验失败时继续执行Pro原流程，失败信息进入状态摘要但不能阻断本来可成功的完整研究。
- 生产验证使用`--source-scout-only`，不得为了测试公众号能力重复发布同日报告或修改成功状态。

## 2026-08-14 市场研判以程序化9分门槛替代主观成熟度声明

- 研究成熟度采用10分制质量合同，覆盖证据3分、来源覆盖2分、滚动分析2分、行动闭环2分和运行可靠性1分；生产最低发布分为9.0。
- 评分只使用报告、历史仓库、独立来源验证和模型调用遥测中的可计算字段，由程序在模型输出后生成，模型不能自报分数。
- 每个同业模块单独满足一手证据要求；来源结构至少达到12组查询、12项来源、4项官方来源、5个发布主体、5个域名和50%一手外部来源。
- 行动提示升级为跨期台账，稳定行动键、进度、验收指标和复核日期属于发布质量合同；微信公众号不设数量硬指标，避免以转载或绕过访问控制换取得分。
- 低于9.0分的报告不得覆盖上一期；单期达到9分后仍继续观察六期，不能用一次成功替代首次成功率和长期稳定性验证。

## 2026-08-14 市场研判采用Pro主研、Flash首修、Pro升级的分层模型组合

- 首次深度研究继续使用`deepseek-v4-pro[1m]`，因为任务需要多源搜索、六期历史、内部快照、监管辨析和条线综合，不能为降本牺牲主判断上限。
- Claude Code的Haiku/轻量子任务和第一次定向修复使用`deepseek-v4-flash`；修复后仍未通过完整门禁时，第二次且仅第二次升级回Pro。
- 格式、计数、历史关系、变化信号和坏源安全剔除继续由确定性程序处理，不使用模型；外部来源仍须独立复核，Flash结果不能降低发布标准。
- 无法安全剔除的坏源在同一进程内进入Flash→Pro修复链，避免先退出并等待systemd整轮重启；两轮后仍失败则保留上一期报告。
- 状态文件只记录模型角色、模型名、耗时、轮次、token、搜索次数和CLI估算成本，不记录提示词、凭据或来源正文；实际费用以DeepSeek账单为准。

## 2026-08-02 市场研判固定在凌晨1点并按成功报告日期保持三天节奏

- 不再使用从服务完成时刻顺延72小时的`OnUnitActiveSec=3d`，避免长时间研究将下一次启动逐步漂移到白天。
- timer每天北京时间凌晨1点触发只读到期检查；最近成功报告日期满3个自然日才启动固定研究服务，不足3天不调用模型。
- 手动研究成功会自然重置后续三天周期；研究失败不更新成功报告日期，调度器在次日凌晨1点重试。服务器错过凌晨1点时保留`Persistent=true`补做检查。
- 定时检查只允许启动固定`market-analysis.service`，不接收网页参数、不读取凭据、不降低既有隔离和证据门禁。

## 2026-08-02 市场研判确定性格式自校准并仅安全剔除冗余坏源

- 来源分类计数和字段长度是报告自身可确定的数据，由程序按实际证据台账和网页契约校准，不再消耗模型修复轮次。
- 独立验证失败来源不得无条件删除。只有每个引用项仍有证据、宏观/监管模块仍保留官方A级、同业模块仍保留一手A/B级、总来源仍不少于8项时才可剔除，并记录研究边界。
- 唯一证据、关键证据等级或剔除后不足发布门槛时必须继续失败，上一期有效报告保持不变。
- 网站漏发中间证书时不得绕过TLS；只允许从证书AIA声明的CA官方地址取得并核验特定中间证书，再由研究验证器复核真实页面。

## 2026-08-02 客户清单网页导入采用预检确认和增量刷新

- 客户分析内新增Excel/CSV入口，但该入口只维护客户—保单关系与当前状态，不导入业绩金额；经营业绩继续走原业绩导入链。
- 正式导入必须同时具备`customer_analysis`和`upload`权限，先预检后确认。预检与确认使用文件清单哈希绑定，文件变化后必须重新预检。
- 同一保单客户归属冲突、必需字段无效或同一快照时间关键状态冲突时整批阻断；导入时间较旧的保单明确跳过，不允许旧快照覆盖新快照。
- 写入只重建受影响客户主表，并更新受影响保单及客户的月度事实；不因小批量增量导入全量重建310万份保单快照。
- 浏览器按8MB分片上传，服务器以受保护临时文件和临时SQLite流式归并，后台处理不占用长连接，不设置固定文件大小、文件数和行数上限。真实容量边界由服务器可用磁盘和处理时间决定。
- 上传原文件只在后台处理期间临时落盘，成功、阻断、失败或24小时未确认后清理；审计仅保留文件校验信息和汇总数量，客户号、保单号及逐行错误不得进入日志、Git、发布包或项目记忆。

## 2026-08-02 市场研判变化信号以当前模块状态为唯一分类源

- 模型继续负责形成模块事实、判断及其 `history.state`，程序不改变持续、强化、反转、新增或失效的业务判断。
- `changeSignals` 不再作为一套可独立漂移的模型分类结果。发布前按当前模块的状态、主题、证据和上一报告编号确定性重建，保证每个模块恰好出现一次。
- 历史主题只有在本期保留相同 `topicKey` 的当前模块、标记为 `expired` 并引用当前失效证据时，才能进入失效信号；没有当前模块的历史残留项直接丢弃。
- 修复检查点中的变化信号映射错误属于确定性错误，优先本地归并并继续校验，不再次调用模型；事实、证据或业务状态问题仍走有上限的模型修复。

## 2026-08-02 新客按系统首现建队列，购买贡献按可追踪业务观察

- 新客身份以`customer_master.first_underwriting_time`为唯一判断依据，不因业务、机构、长险或产品筛选而改变；页面同时展示系统新客和筛选范围内可追踪新客，避免把部门业绩覆盖人数误写成系统全部新客。
- 后续经营提供首现月、首现后12个月和首现当年度三个观察窗口。滚动12个月采用`[首次承保日, 首次承保日+12个月)`，满12个月当日不计入；未走完整窗口的客户单列，不把未成熟队列当成完整复购表现。
- 再次承保以系统首张保单号为基准，其他保单均计为再次承保；同日多单也只保留一张首单。产品、保费和再次承保限定为当前可关联的OTO、证保、蚁桥业绩，界面明确这一范围。
- 产品维度通过已有投保单号索引按需关联`performance`。全量库实测整年新客产品查询约0.2秒，完整接口约0.75秒，因此不新增客户事实产品列、不触发5GB生产库结构迁移。

## 2026-08-02 全量历史库继续使用SQLite并采用“聚合优先、年度回退、按需加载”

- 本次变慢不是SQLite无法承载517万行业绩，而是交互接口存在全表读入、日期表达式扫描和重复请求。完整副本重建、完整性检查及聚合查询实测通过，因此不启动MariaDB迁移。
- 队伍交互查询以人员月度聚合为主，产品交互查询以产品日级聚合为主；原始明细只作为兼容回退，必须先用可索引的年度范围限制读取规模。
- 聚合保留原业务筛选和统计边界。队伍未指定业务模式时继续汇总人员名下全部业绩，不能因聚合表只关注OTO、证保、蚁桥而缩小既有口径。
- 折叠模块不属于首屏必需数据，统一在用户展开时加载；同一年度加载链路已取得的数据应直接复用，不重复请求。
- 数据库迁移只在聚合后查询仍不能达到使用要求、并发写入或高并发读取成为实际瓶颈、备份恢复窗口不可接受等触发条件出现时重新评估。

## 2026-08-01 全量历史与客户分析采用“离线候选库 + 保单快照”

- 继续使用SQLite，不启动MariaDB迁移。517万条业绩、310万份保单快照和约11万条OTO/证保/蚁桥保单月事实在当前查询和单写者边界内可用；架构迁移仍按既有评估触发条件另行决策。
- 2026-07-31全量业绩文件晚于原生产库数据版本。重叠月份先对账，再由全量源替换原生产业绩；旧生产库通过SQLite Online Backup保留，不在运行库中混合两套保单号长度和字段版本。
- 客户CSV不逐行并入业绩表。先按投保单号归并一保单一快照，再构建客户主表和保单月事实，避免客户源多行造成保费、件数和客户数放大。
- 客户源重复保单没有状态、客户或承保时间冲突，只存在入账时间多值，因此保单快照保留最早/最晚入账时间和源记录数，不保存重复客户源行。
- 新客/老客以客户清单覆盖范围内的首次承保日期和所选期间起始日划分；无法关联的业绩单列，不默认归为老客。
- 当前客户清单只提供数据截止日状态，不具备应缴、实缴和续期保费序列，因此本模块展示“当前有效率、停效、退保及终止原因”，明确不命名为继续率。

## 2026-07-02 荣誉体系冲销/退保按有效正向保单净额处理

### 决策

星钻联盟荣誉体系中，正向保单先判断是否符合星钻统计条件；已计入统计的正向保单，如后续出现同一投保单号的负向冲销/退保记录，则负向标保和负向件数参与净额扣回。正向保单本身未计入统计的，负向记录不再重复扣减。负向冲销的团队扣回沿用对应有效正向保单的团队归属。源表显式 `承保件数=0` 的调整记录按 0 件处理，不默认算作 1 件长险。

### 原因

- 直接丢弃负向记录会高估月度标保、长险件数、证保季度通算、团队标保和团队星钻人力。
- 无条件扣回所有负向记录会低估结果，因为部分正向保单本身因未回销或超期已未计入星钻统计。
- 同事底稿的 2026 年 6 月清单验证了该净额边界：修正后系统 `59` 个会员身份轨道与同事底稿总数、机构、业务线、等级和逐人名单一致。

### 影响

- 后续调整荣誉体系源数据加载时，不得恢复为“负数记录全部丢弃”或“负数记录无条件扣回”。
- 个人月度达标、证保季度通算、主管/经理团队达标和 dashboard 源保单统计均应使用净额后的标保和件数。
- 若负向冲销行缺少主管/经理工号或团队归属与正向行不一致，团队扣回以已计入的正向保单归属为准，避免个人净额和团队净额不一致。
- 如未来能引入更权威的保单状态字段，可在此边界上进一步区分撤单、犹退、退保、冲正等类型，但不能破坏同一投保单号净额追溯。

## 2026-07-02 荣誉体系按身份轨道分别计算

### 决策

星钻联盟人员计算以“人员 + 身份轨道”为连续计算单元。个人轨道、主管团队轨道、经理团队轨道分别维护星曜钻石余额、获钻、扣减和会员等级；同一管理职人员既可以有个人轨道，也可以有主管/经理团队轨道，两者不合并计算。

- 旧实现把个人达标和团队达标合并到同一人员余额，会把主管/经理的个人连续和管理职团队连续串在一起，导致机构角色列和会员等级误判。

### 影响

- 荣誉明细和汇总的唯一键必须包含 `role_type`；同一人员同一业务线允许同时存在 `个人` 与 `主管/经理` 记录。
- 团队历史中的团队会员人数继续按团队成员个人轨道判断；管理职自身团队轨道仅用于其主管/经理身份获钻和等级。
- 剩余无法由方案原文解释的清单差异，应先落入待确认问题，不得通过硬编码名单或无字段依据的过滤规则处理。

## 2026-06-30 前端控件事件采用声明式属性与模块绑定

### 决策

主看板页面和 `js` 目录内的用户交互控件不再新增 `onclick` / `onchange` 内联事件。静态页面控件使用 `data-*` 声明行为，动态模板控件使用所属模块的容器级事件代理。

- 静态测试已覆盖主要控件的防回退约束，可以在后续迭代中及时发现维护性倒退。

### 影响

- 后续新增按钮、下拉框、复选框或动态输入框时，优先添加语义化 `data-*` 属性，并在所属 `js` 模块集中绑定。
- 不在 HTML 字符串里拼接业务函数调用；需要复用业务逻辑时，保留函数作为模块内部入口，由绑定层调用。
- 若确需临时使用内联事件，必须同步记录原因并补充迁移 TODO。

## 2026-06-30 KPI 日级 YTD 查询集中到内部 helper

### 决策

`get_kpi_data()` 中读取日级累计表的 YTD 查询，统一通过 `_sum_daily_columns()` 和 `_sum_daily_column_by_channel()` 生成并执行。转型业务、经代业务和产品类指标继续按各自真实日级截止读取。

### 原因

- KPI 概览同时涉及转型日表、经代日表、机构产品日表，重复拼接 `date_filter_sql()` 和 `SUM(...)` 容易在新增指标时出现漏改或字段别名不一致。
- 近期 `asOf`、产品分类和经代/转型不同截止日规则已经成为核心业务边界，日级查询应有统一入口，便于审查和回归。
- 当前性能与维护收益可以通过 Python 内部 helper 获得，不需要为了这类查询改写为 Rust。

### 影响

- KPI 接口字段、月级回退策略、长险期交口径和前端展示不变。
- 后续新增 KPI 日级 YTD 指标时，优先复用这两个 helper；如果需要按业务线不同截止日混合查询，应继续使用 `cutoff_policy` 生成截止条件。
- helper 内置 SQL identifier 校验，后续不得把未校验的用户输入作为表名或列名传入。

## 2026-06-30 原始表日期过滤集中到 raw_table_reader

### 决策

直接读取 `performance`、`jingdai`、`hr_data`、`value_data` 等原始 Excel 表时，候选列选择、日期字段压缩、年份/月度过滤和截止日过滤优先使用 `services.raw_table_reader` 中的公共 helper。

### 原因

- 原始表字段多为中文列名且格式不稳定，日期可能出现 `YYYYMMDD`、`YYYY-MM-DD`、`YYYY.MM.DD`、中文年月日等形式。

- `raw_table_reader` 已是原始表读取边界，将列选择和期间过滤放在同一服务更便于复用和测试。

### 影响

- 产品结构与各业务模式前三产品查询业务口径不变，但复用公共 helper。
- 后续新增直接读原始表的分析模块，应优先使用 `pick_existing_column()`、`append_period_filter()`、`append_cutoff_filter()`，不要在 repository 内重新实现日期清洗 SQL。
