# “现行销售产品分析”模块初稿
**可行性判断：可以在现有 FastAPI、SQLite 和独立分析页架构上实现。决定工作量的主要因素是产品资料，而非页面技术。** 现有经营 Excel 能识别部分产品名称、代码和销售结构，但不足以证明产品当前可售，也不包含完整责任条款和逐日利益现金流，不能直接用于责任对比或 IRR 排名。

## 1. 项目现状

项目当前由 FastAPI 提供接口和页面，SQLite 保存经营明细及聚合数据，前端使用原生 HTML/JS 和 ECharts。主看板已有“产品结构”模块，按产品分类、保费和件数分析销售结果；[产品接口](../backend/api/product.py)和[数据流说明](../docs/数据流说明.md)表明它不是产品条款库。[市场研判](../docs/MARKET_ANALYSIS.md)已有带来源的寿险产品专题，可提供竞品线索，但其定期研究结果也不能直接充当“现行在售”名录。

[网点分析](../branch-analysis.html)、[客户分析](../customer-analysis.html)等采用独立页面、页签、筛选、来源及口径提示；新模块适合沿用这一形态。另需注意：本工作区 Git 为 `453889a`，[项目上下文](../docs/ai-context/PROJECT_CONTEXT.md)记载生产已更新至 v1.0.159。实施应先对齐最新生产源码。较早的[需求文档](../需求文档.md)仍描述纯浏览器方案，本次设计应以当前代码和部署规则为准。

## 2. 数据来源与建议结构

以**产品代码＋条款/费率版本＋销售渠道＋有效期间**标识一款可比较产品；同名产品的不同版本不能合并。建议先由产品管理人员提供并确认内部资料：现售清单及上下架通知、正式条款、产品说明书、费率和现金价值/利益演示表、服务权益规则。竞品使用保险公司公开条款、产品说明及有效的销售状态资料；市场研判中的线索需重新核验。每条关键事实记录文件版本、发布日期、页码或表格位置、核验人与核验时间。

| 建议表 | 核心字段 |
|---|---|
| `sales_product_versions` | 产品 ID、公司、代码、名称、责任类型、利益机制、条款版本、适用渠道/地区、销售状态、状态有效起止日、资料核验状态 |
| `sales_product_responsibilities` | 产品版本 ID、责任类别、触发条件、给付规则、等待期、责任免除、适用条件、来源位置 |
| `sales_product_scenarios` | 产品版本 ID、方案 ID、年龄/性别等费率条件、保额、缴费安排、领取及退出情景、保证/非保证标识、报价或模拟状态 |
| `sales_product_cashflows` | 方案 ID、现金流日期、类型、金额、币种、是否已包含于合计、来源位置 |
| `sales_product_claims`、`sales_product_sources` | 卖点或比较判断、成立条件、限制、证据 ID；来源标题、版本、链接或受保护文件位置、哈希、页码、核验状态 |

录入格式可先采用一份 XLSX，按上述内容分为“产品版本、责任、测算方案、现金流、卖点、来源”六个工作表；导入前预检主键、版本、日期、单位、来源引用及现金流完整性。原始条款和利益表放在受保护的数据位置，不进入 Git 或 Docker 镜像。现有 `product_config` 只维护经代产品分类，不建议扩成条款库。

## 3. 页面、接口与计算

建议新建“现行销售产品分析”独立页，设四个页签：**责任对比、IRR 对比、卖点对比、竞品对比**。顶部统一选择产品版本、渠道和比较基准日；表格逐项显示“相同、差异、缺资料”，并能打开对应证据。卖点先由经核验的责任和利益事实人工编写、审批；后续可增加草稿辅助，但不能让自动生成内容直接成为销售表述。

后端单设 `/api/sales-products` 系列接口，提供名录、版本详情、责任与卖点、同条件比较、IRR 测算，以及管理员预检/导入/发布。计算逻辑放在后端，前端只展示输入、现金流和结果，避免页面间出现两套公式。

**IRR 口径先固定为“明确情景下的客户现金流年化收益率”。** 保费为负，实际可领取金额为正；退保情景计已领款和该日可领取退保额，满期、身故等互斥情景分别计算。按实际日期求解  
`Σ CFᵢ / (1+r)^((日期ᵢ−首笔日期)/365) = 0`。保证利益与非保证演示分列；红利留存、现金价值及总利益须检查重复计入。后端返回结果时同时给出现金流、情景、日计数口径、NPV 残差和数据状态；缺关键数据、无解或可能存在多根时显示“不可计算/待复核”，不填 `0%`。比较界面必须同时展示投保条件、总保费、缴费时点和退出年，条件不同的结果不直接排名。保障责任强的产品也不能只凭 IRR 判定优劣。

## 4. 与现有看板衔接

页面沿用现有分析页的顶部导航、卡片/表格、空状态和“口径与质量”区域，并在主看板加入受权限控制的入口。建议新增独立读取权限 `sales_product_analysis` 和维护权限 `sales_product_manage`；前端隐藏入口之外，所有接口仍由后端校验。[现有权限实现](../backend/auth.py)可作为接入点。

新表通过[现有数据库初始化与迁移机制](../backend/db/schema.py)建立，与经营 Excel 聚合链路分开；单纯新增产品资料表不应触发历史保费聚合重建。发布时补齐 FastAPI 页面路由和 Ubuntu 备用 nginx 的静态白名单，并按[AGENTS.md](../AGENTS.md)同时验收本机 API 与正式公网 HTTPS 的页面、鉴权和数据。

## 5. 分期实施

1. **一期：可核验的人工维护版。** 对齐最新源码；确定首批产品和统一测算方案；建立版本化资料表、XLSX 预检导入、独立页面和权限。先覆盖少量已核验的自有产品及直接竞品，交付四类对比；IRR 只对现金流完整的方案计算，其余明确显示缺项。验收重点是逐项回溯原文、独立复算 IRR、版本/上下架切换和权限隔离。
2. **二期：维护效率与比较深度。** 增加版本差异、批量更新、更多缴费/领取情景、非保证情景及历史快照；将市场研判的产品线索转为待核候选，经过人工核验后再入正式产品库。
3. **后续：经营联动。** 在产品代码和版本映射可靠后，关联销售结构、渠道表现及客户适配分析。经营实绩、客户收益和竞品判断继续保持各自的数据口径。

## 6. 主要风险与待确认事项

最大风险是**资料不全却显示精确比较结果**：销售状态可能随渠道和地区变化；演示表可能缺领取日期或退出金额；同名产品可能换版；宣传卖点可能省略给付条件。处理原则是保留版本和证据、传播“待核”状态，不以保费数据、宣传页或旧上市消息补造条款及 IRR。

实施前请确认三件事：

1. 首批范围：只含我司产品，还是同时纳入哪些公司和竞品？“现行销售”按哪些渠道、地区及基准日认定？
2. 能提供哪些正式资料，尤其是**逐期缴费、领取、现金价值及非保证演示表**？首期 IRR 是否先限于保证利益与指定退保/满期情景？
3. 谁负责确认在售状态、条款版本和卖点发布？普通用户是否可查看竞品及利益测算，还是仅向高级用户开放？

本次完成的是仓库只读评估与规划；未改代码、数据库或部署配置，也未核验任何具体产品的当前销售状态。
