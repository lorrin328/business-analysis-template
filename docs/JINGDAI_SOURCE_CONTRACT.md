# 经代基表与历史数据口径（2026-10-26）

## 当前标准

未来经代导入以 `excel/JD` 中2026-10-26重新提供的14列结构为准；2025年及以后使用新明细，2020—2024年沿用原有数据，仅转换结构。保留原件只读，不把Excel或运行数据库提交Git。版本v1.0.168。

| 新源列 | 存储与用途 |
|---|---|
| 统计时间_年月日 | 转换为真实ISO业务日；同时提供兼容列“时间” |
| 销售平台 | 同时提供兼容列“经代机构” |

| 期交保费、年化规保 | 原始元金额及正负、零全部保留；年化规保同时提供旧别名“承保年化规保” |

## 承保件数与历史平移

用户已确认：新源按所选统计范围内非空投保单号去重，同一单号多条记录保费全部保留、件数只计一次。该口径含冲正记录，不能解释成净承保件数。

原始表统一增加“承保件数”“件数来源”“经代源格式”。新源“承保件数”是日×平台×产品×交期×投保单号粒度的首次出现贡献，首条为1、其余为0；空单号为NULL。此字段用于日粒度复算，不能跨日期、平台、产品直接相加作为任意范围件数。产品、交期及件均API通过独立保单日事实表重新去重，前端显示口径说明。

2020—2024年旧源继续保留原始承保件数净额，包括零和负向冲正，标记 `legacy_aggregate` / `source_net`。仅补足真实别名和缺失字段，不生成虚拟投保单号，不拆分汇总行，不补造产品代码、长短险或产品标志。月级时间保留月精度。旧新口径分别披露；混合范围件数及件均不能作为统一可比结果。保费金额仍可汇总。

本地原始经代表仅有2025、2026年；另保留2022、2023年历史汇总。按用户最新确认，已将本次导入的2024年不完整新明细及其派生汇总撤回，历史分区与导入前恢复副本逐值一致。没有原始明细的历史汇总也必须在聚合重建时保留，不能清零、反推明细或生成虚拟单号。本地未包含2020、2021、2024年经代原数据，这部分仍以生产原库为准，本次没有修改生产。

## 导入与补齐

网页经代栏允许多选日期不重叠的分文件，同批合并后按整月替换；同月补齐时要同时选择该月全部分片，不能只上传缺失片而删除其他片。同批任一经代分片失败则整批不写；已经导入的同月分片也不得跳过后再只写新片。源内相同交易行不擅自去重，重建聚合保留行数和金额。

新旧源均可识别；2020—2024年只接受原历史结构转换，不接受新投保单号明细覆盖；旧汇总格式不得覆盖2025年及以后已存在投保单号明细的月份。未来新增字段自动扩列保留；真实数据缺失保持NULL，不能以0掩盖。文件达到100万行时预览明确警告。本轮2020—2024年历史不更换来源。

当前代理请求上限与后端单文件上限分别管理；多个年度宜分批导入，不把本地成功等同于线上大请求已通过。

## 迁移与恢复

新迁移 `20261025_jingdai_policy_identity`、`20261026_jingdai_source_contract` 均要求从现有原始数据重建聚合。原始表自动扩列和一次性别名回填保留源行、保费与旧件数。

`backend/migrate_jingdai_sources.py` 默认仅输出来源清单和历史保护范围；正式生成候选库时自动跳过全部落在2020—2024年的新明细文件，跨越旧新口径边界的混合文件拒绝整批写入；`--apply` 需要指定代码目录外的恢复目录，只生成包含在线恢复副本、候选库和审核记录的迁移结果。候选库逐月勾稽、完整性、保留表摘要、接口校验通过后，才能替换目标库。不能将候选库生成成功当作已发布。

2026-10-26用户已授权同步GitHub并部署Ubuntu。生产发布保留2020—2024原有数据，仅导入2025—2026新基表；生产验收另记工作日志。市场研判保持暂停，不触发研究。

本次范围修正另存 `history_scope_correction.json` 及修正前恢复副本；2025—2026年及其他业务数据摘要逐值不变。

发布门禁补充：2020—2024年既有经代月/日汇总及共享表经代分区一律保留，原始数据仅部分月份存在也不得覆盖；新保单日事实中的旧源记录仅作追溯，历史接口仍使用保留汇总的原承保件数，防止部分事实压低全年件数。
