# “现行销售产品分析”模块规划 v2

规划日期：2026-09-25。交付性质：规划修订，尚未实施代码、数据库或部署变更。适用对象：有权查看内部产品研究资料的产品、渠道和经营分析人员。

## 一、定位与本次修订

本模块在现有 FastAPI、SQLite 和独立分析页架构上建设，以“特定客户需求、渠道、产品版本和持有情景下，哪些差异有证据支持”为核心问题。页面名称保留“现行销售产品分析”，但产品进入“现行销售”范围必须有**指定基准日、渠道和地区的正式可售证据**。007 项目的历史材料、开发稿和 IRR 结果只是研究底座，不自动证明当前可售。

相对上一版，数据来源改为**007 项目结构化成果的受控转换与增量补录**：逐款责任和利益机制取 `OTO事实.json`、`证保事实.json`、`开发事实.json`；IRR 与逐笔现金流取 `20260924_分缴别IRR` 下两渠道 `results.json` 和 `combined_results.json`；文件归属与完整性取 `产品分类基线.json`、`资料索引.csv`。上一版建议的六张逻辑表保留，但首批数据不再依赖从零制作六页 XLSX。XLSX 只用于经授权人员补录缺口，且须走同一预检、审批和追溯流程。

007 已有的比较框架、事实状态和更正记录是设计基准；其中“资料有记录”“算术复算通过”“合同口径已确认”“当前可售”是四件不同的事，不能合并成一个通过标志。

## 二、导入边界与六表映射

导入程序只读访问 007，经受控中转区完成字段校验、版本绑定、来源核对和人工复核，再写入本看板独立产品资料表。运行库及中转件放在受保护的数据目录；不把 007 原始 JSON、条款、利益表、PDF 提取文本或源路径清单提交 Git、打入 Docker 镜像或暴露给浏览器。导入批次记录输入文件哈希、007 核验日期、转换规则版本、导入时间、审核人与异常清单；相同批次重复导入应幂等，可撤回未发布批次。

|---|---|---|

| `sales_product_claims` | 三份事实 JSON 的责任差异、利益机制和限制可生成**内部比较命题草稿**，并关联产品、渠道、情景及证据；底层总报告可作线索索引。 | 面向销售使用的卖点文案、成立条件、禁用表述、适用客户与审批人必须人工确认；研究判断不自动成为销售话术。 |

## 三、继承 007 的 IRR 口径与复算验收

同条件保证利益比较沿用 007 的**40 岁女性、计划总保费 150 万元**基准：趸交 150 万元，三年交每年 50 万元，其余缴期按总保费除以期数；保费在 `t=0,1,…` 年初支付，指定第 H 年末退出。提前退出只计已支付的保费，不能把未来未交款计入投入。原表金额线性缩放仅是数学比较；不满足最低保费/保额或核保准入的行必须标“数学模拟，非正式报价”。不同保险期间、起领年龄、领取频次和产品类别分组展示，不能因预算相同就作无条件总排名。

原底稿用保单年度 `time_year` 求解 `Σ CFₜ/(1+r)^t=0`，同一时点现金流合并检查符号并用二分法求根；它不是按实际日历天数求 XIRR。保证退保、满期、身故/疾病及其他互斥情景分别建模；退保收益可计退出前已领的保证金及该时点可领退保价值，同一时点已含在现金价值内的给付、红利价值不能重复加。保证、说明书非保证演示、万能结息假设、开发稿载值和开发稿可复算满期情景分库存储及展示；不把红利保额当现金领取，也不把演示投资利率上限当本款已确认参数。

`combined_results.json` 中 `records` 共 527 条：511 条有数值的同条件保证 IRR、16 条养老金起领后观察点为待核空值；对应 106 个缴别/方案组合、15 款正式材料产品。`all_calculations` 为 774 条有数值的算术复算范围，包含保证、原说明书演示、万能假设及 5 条开发稿满期复算，**不是 774 条均已完成合同边界核验**。其中两条演示结果仍有第 30 年退出与首期给付、现金价值衔接的时点警示。开发终身寿 80 岁稿载 IRR 缺完整逐年现金流，不纳入已复算结果。导入时保留 `records`、`example_records`、`development_maturity` 的来源分区与唯一 `result_id`；`guaranteed_groups` 只作展示索引，避免重复入库。

预检逐条核 `result_id` 唯一性、产品/版本绑定、现金流至少一正一负、缴费合计和退出已交额、来源引用、包含关系、缺失状态及互斥情景；独立求根后与原 `irr` 比较，并计算 NPV 残差。以 007 既有验收为回归基线：774 条工作簿公式与独立计算最大差约 `7.16×10⁻¹¹`，合并底稿最大 NPV 残差约 `3.95×10⁻⁸` 元；转换后要求记录条数、空值数和来源分区一致，差异须逐项解释。页面返回 IRR、现金流、条件、口径、算术校验状态和合同核验状态；缺关键输入、无唯一可用根或边界待核时显示原因和 `null`，不填 `0%`。未来如需真实日历日期 XIRR，另设方法版本和独立验证，不能覆盖本批年度 IRR。

## 四、比较框架、页面和权限

页面沿用独立分析页形态，先让使用者建立**比较合同**：本品与替代品的正式名称/代码/版本、公司、渠道、地区、资料基准日、可售状态，以及客户需求、年龄、性别、核保条件、币种、预算、缴费时点、保障期、起领与退出时点、红利处理。不能对齐的条件在结果上方常驻显示差异及影响，硬约束（适当性、支付能力、流动性、销售资质）先于优势排序。

核心是 007 框架的七维证据矩阵：**客户需求、保障责任、利益水平、退出与灵活性、服务权益、渠道承接、公司经济性**。四个页签继续保留“责任对比、IRR 对比、卖点对比、竞品对比”，但每个差异都能回到矩阵中的维度、适用条件、来源页/条款、核验日期和限制。医疗/重疾/意外优先展示保障、免赔、续保和核保；储蓄/养老强化现金流与长期持有；万能主险和账户资金流拆开。客户价值、渠道承接和公司经济性分别给结论；缺 NBV、CSM、费用、资负或资本资料时不作公司价值排序。

证据状态在**事实/结果行**上显示为“已确认 / 开发稿载 / 假设下复算 / 待核”，并另列“算术校验”和“现售核验”状态。已确认只在适用的原件版本、条件和核验范围内成立；开发稿载只说明原稿内容；假设下复算不自动确认输入和合同边界。表格显示“优势、短板、相当、未知”及成立条件，不默认给总分；确需评分时先公布权重、锚点、缺失处理和敏感性，缺失不算零分。卖点以事实记录生成草稿后经产品/合规授权审定，展示时带限制，不生成“保证高收益、无条件赔付、随时无损退出”等表述。

后端提供独立的名录、版本详情、证据矩阵、责任/卖点、IRR、竞品与受控导入接口；读取与维护分别授权，前端隐藏入口之外所有 API 均在后端鉴权。开发稿在列表、详情、比较结果、导出和 API 中显著标注**“开发稿，不代表在售”**，默认不进入“现行销售”筛选。原始条款和利益表只在受保护文件服务中按权限访问，公开静态目录、Git、镜像和接口响应均不得泄露原件或服务器路径。新增产品资料迁移与经营 Excel 聚合链路分开；发布时按本项目 AGENTS.md 验收本机 API、正式公网 HTTPS 页面/API、鉴权、静态资源和业务数据。

## 五、责任、卖点和竞品的具体来源

责任对比先把 `OTO事实.json` 的 13 个合同产品、`证保事实.json` 的 9 款核心产品，以及 `开发事实.json` 的 5 款开发稿分别转为可审条目。OTO 以产品名和来源 ID 关联，代码须补证；证保按代码与适用条款来源关联；开发稿按代码、稿件哈希和 Word 表格定位关联。逐条拆成“责任类别—触发条件—给付/限制—除外/等待—证据—状态”；无法无歧义拆解的原文保留为待核，不凭算法简化成年期、未成年或缴费期内外分支。服务权益和保险责任分开，现金红利用途与增额红利机制分开。卖点只能从已核责任、利益和限制生成可审命题，不能直接复制宣传页或底层总报告中的经营判断。

007 的 `05-竞品资料` 当前无文件；底层总报告列有有限的官网竞品来源，可作候选线索，包含历史停售对照，不能当成当前在售竞品库。二期按客户需求和同类/跨类替代关系建立候选池，从保险公司官网公开条款、产品说明、现行目录和可核验报价获取正式资料，记录公司、版本、访问日、渠道地区、销售状态与链接/哈希；动态在售状态在每次发布或引用前重核。竞品没有同条件利益表时先做责任与机制对比，IRR 显示缺证据；旧版只作历史/存量对照。公开来源与 007 内部资料分库、分权限和证据状态展示，内部材料严禁外发。

## 六、分期实施与验收

1. **准备期：数据合同与安全边界。** 核对当前源码/迁移/鉴权实现，锁定产品主键、渠道地区与状态字段；对 007 结构化文件做只读哈希快照和字段映射，完成 165 条分类基线与 159 条资料索引的差异表，列出 OTO 代码、版本、现售和来源缺口。产出可审的导入样例与异常清单。
2. **一期：自有产品内部比较。** 建六表、受控导入与复算校验；先发布有身份和来源证据的责任矩阵及 511 条同条件保证结果中可解释的记录，16 条待核继续为空。原案例演示、开发稿和数学模拟分区展示；补齐权限、页面、导出警示及卖点审核。验收至少覆盖逐条溯源、774 条数值回归、空值保持、版本/渠道隔离、开发稿提示和越权访问拒绝。若当前可售证据尚未提供，页面先以“产品研究资料”内部预览，不宣称“现行销售”。
3. **二期：竞品与深度情景。** 按正式公开来源建竞品候选及状态维护，补同条件正式建议书、养老金月领时点和连续现金流、非保证演示及费用/服务规则；每个新增情景单独核合同与复算。只有证据充分时才扩展卖点或比较结论。
4. **后续：经营联动。** 产品代码、版本、渠道和有效期映射稳定后，再联接看板销售结构与客户适配；经营实绩、客户收益、竞品证据和公司经济性继续分账。每阶段仅在完成本地/公网、权限、数据和来源验收后发布，不因健康接口通过就视为上线完成。

## 七、实施前待确认

1. “现行销售”的基准日、渠道、地区及权威可售清单由谁提供和确认？开发稿是否仅供产品管理角色查看？
2. 007 内部派生数据进入本看板受保护运行库的授权范围、审核人和允许的用户角色是什么？原件定位是只保留来源编号，还是提供经过鉴权的内部跳转？
3. 首批比较合同覆盖哪些已确认版本；OTO 无代码或一文件多产品的映射由谁复核？销售卖点由谁审定？
4. 竞品首批名单与同条件建议书能否取得；两款养老金第 30/40 年的给付、退出时点和月度序列由谁补证？

这些问题影响发布范围，不妨碍先完成只读映射、缺口台账和内部导入样例。007 目录保持只读；本规划未核验 2026-09-25 的实际可售状态，也未把任何开发稿视为已批准产品。
